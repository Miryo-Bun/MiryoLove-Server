# MiryoLove Server

MiryoLove Server — серверная часть и основа REST API экосистемы MiryoLove. Реализованы регистрация и вход, серверные сессии, профили, чаты, сообщения, PostgreSQL, необязательная авторизация Google/Yandex и защищённый AI endpoint.

Сайт находится в отдельном проекте `../MiryoLove AI Web`. При первом авторизованном запросе сервер запускает существующий Python-скрипт с моделью как постоянный локальный runtime.

## Продукты и языковая политика

Это отдельные продукты:

- **MiryoLove Server** — этот сервер и REST API.
- **MiryoLove AI Web** — отдельное браузерное приложение EN/RU.
- **MiryoLove AI** — существующая Python-логика и готовые веса в отдельных каталогах.
- **MiryoLove Training** — будущая система обучения моделей, не входящая в проект.

Английский — основной язык проекта и интерфейса; также поддерживается только русский. Текущий API не хранит выбранную локаль и не локализует тексты ответов.

## Архитектура

```text
MiryoLove AI Web
        | HTTPS / REST API с сессионной cookie
        v
MiryoLove Server
        +---- Маршруты и контроллеры Express
        +---- Контракты сервисов авторизации, профиля, чатов, OAuth и ИИ
        +---- PostgreSQL через Prisma
        +---- Google OAuth 2.0 / Yandex ID (необязательно)
        +---- Постоянный Python AI Runtime (существующий скрипт и модель)
        +---- MiryoWiki MediaWiki API и поиск в русской/английской Wikipedia
```

HTTP-слой разделён на маршруты, контроллеры, схемы Zod, middleware и сервисы. Prisma подключается к PostgreSQL. Runtime запускается по первому запросу и загружает модель один раз; запросы генерации выполняются последовательно. Существующий Python-скрипт ищет в MiryoWiki и Wikipedia на языке вопроса только для явных энциклопедических запросов. Источники сохраняются вместе с ответами.

## Реализованные возможности

- Регистрация и вход по email и паролю; пароли хешируются Argon2id.
- Непрозрачные серверные сессии в PostgreSQL; браузеру выдаётся только HTTP-only cookie с `SameSite=Lax` и `Path=/api`, а в production — также с `Secure`. Токен сессии не возвращается в JSON и не хранится в Web Storage.
- Получение текущего пользователя, чтение и обновление профиля.
- Создание, просмотр списка, чтение, переименование и удаление собственных чатов.
- Создание и просмотр сообщений в принадлежащем пользователю чате.
- Необязательная авторизация OAuth через Google и Yandex по коду авторизации.
- Авторизованный AI-чат с готовой моделью и сохранением истории.
- Поиск MiryoWiki/Wikipedia и сохранение ссылок, если текст источника попал в контекст модели.
- Ссылки на источники сообщений в nullable JSONB PostgreSQL.
- Проверки доступности, валидация запросов, JSON-ошибки, журналирование запросов, ограничения частоты запросов и OpenAPI/Swagger в режиме разработки.

Публичный маршрут создания сообщения принимает только роль `user`. Сообщения `assistant` и `system` создаются только доверенным серверным кодом. AI endpoint сохраняет сообщения пользователя и помощника после успешной генерации. Выход очищает cookie и при истёкшей серверной сессии.

## Технологии

- Node.js 20.19 или новее; рекомендуется Node.js 22 или более новая LTS-версия.
- TypeScript в строгом режиме и Express 5.
- PostgreSQL 17 и Prisma ORM 7.
- Zod, Argon2id, `cookie` и непрозрачные серверные сессии с HMAC-хешированием.
- Необязательные Google OAuth 2.0 и Yandex ID OAuth.
- Pino, Helmet, CORS и проверка Origin по точному списку разрешённых источников, ограничения частоты запросов. CSRF-защита сочетает cookie `SameSite=Lax` с backend-проверкой Origin; изменяющие состояние операции приложения не используют GET.
- Vitest, Supertest, ESLint и Prettier.
- Swagger UI по `/docs` и JSON OpenAPI по `/openapi.json` только в режиме разработки.

## Требования

- Node.js 20.19+ и npm.
- PostgreSQL 17: локально или через Docker Compose.
- Docker Compose необязателен, если PostgreSQL уже доступен отдельно.

## PostgreSQL через Docker Compose

Конфигурация Compose запускает только PostgreSQL. Данные хранятся в именованном томе `miryolove-postgres-data`; по умолчанию порт публикуется только на `127.0.0.1`.

```sh
docker compose up -d
docker compose ps
```

Настройки Compose можно передавать через окружение. При изменении параметров PostgreSQL убедитесь, что `DATABASE_URL` указывает на тот же хост, порт, базу и пользователя. Не открывайте учётные данные разработки для доступа из публичной сети.

Остановить сервис, сохранив именованный том с данными:

```sh
docker compose down
```

Не удаляйте том и не редактируйте `postgres-data/` в рамках обычной очистки. Разрушительные операции с базой или томом требуют явного решения о хранении данных и проверенной резервной копии.

## Prisma и миграции

Сгенерировать Prisma Client:

```sh
npm run db:generate
```

Для разработки миграций предусмотрена команда:

```sh
npm run db:migrate
```

Для применения проверенных миграций к целевой базе:

```sh
npm run db:deploy
```

`db:migrate` и `db:deploy` подключаются к базе из `DATABASE_URL` и могут изменить её схему. Перед запуском проверьте целевое окружение. Не используйте production- или пользовательскую базу для экспериментов. Новые миграции сначала проверяйте на отдельной временной базе PostgreSQL.

Другие доступные команды Prisma:

```sh
npm run db:studio
```

Схема описывает пользователей, OAuth-аккаунты, сессии, чаты и сообщения. Используются UUID, уникальные ограничения для email и аккаунтов провайдеров, внешние ключи с каскадным поведением, перечисления PostgreSQL и индексы для срока действия сессий, списков чатов и сообщений. Хеши паролей и исходные токены сессий не возвращаются API; в базе хранится только HMAC-хеш случайного токена сессии.

Запустить сервер разработки с наблюдением за файлами:

```sh
npm run dev
```

Собрать проект (сгенерировать Prisma Client и скомпилировать TypeScript), затем запустить собранный сервер:

## Настройка OAuth (необязательно)

Email/пароль работают без OAuth. Конфигурация OAuth необязательна. Не добавляйте секреты клиентов в систему контроля версий.

### Google

1. Создайте OAuth 2.0 Web client и настройте экран согласия.
2. Для разработки зарегистрируйте адрес перенаправления `http://localhost:3001/api/auth/google/callback`.
3. Задайте `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` и `GOOGLE_CALLBACK_URL` в локальном окружении.
4. Начните авторизацию запросом `GET /api/auth/google`.

Сервер использует поток authorization code с областями `openid email profile`, сверяет случайное значение state с краткоживущей HTTP-only cookie и требует подтверждённый адрес Google. Токены доступа провайдера не сохраняются.

### Yandex ID

1. Зарегистрируйте OAuth-приложение в Yandex ID.
2. Для локальной разработки добавьте callback `http://localhost:3001/api/auth/yandex/callback`.
3. Задайте `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET` и `YANDEX_CALLBACK_URL` в локальном окружении.
4. Начните авторизацию запросом `GET /api/auth/yandex`.

Сервер обменивает код авторизации на данные профиля провайдера и использует ту же защиту state-cookie. Токены доступа провайдера не сохраняются. Ошибки провайдера и конфигурации журналируются без кодов авторизации, значений state, клиентских секретов и токенов доступа.

Если адрес провайдера уже принадлежит существующему аккаунту, сервер возвращает `ACCOUNT_LINKING_REQUIRED` и не объединяет аккаунты автоматически. Авторизованная привязка и отвязка провайдеров не реализованы.

## REST API

Все JSON-ошибки имеют форму:

```json
{ "error": { "code": "ERROR_CODE", "message": "Сообщение для пользователя." } }
```

Защищённые маршруты используют HTTP-only cookie `miryolove_session`. Сервер не выдаёт фронтенду bearer-токен. Для браузерных запросов используйте передачу cookie и разрешённый Origin.

| Метод    | Путь                          | Авторизация | Назначение                                                                |
| -------- | ----------------------------- | ----------- | ------------------------------------------------------------------------- |
| `GET`    | `/health`                     | Нет         | Состояние сервиса.                                                        |
| `GET`    | `/health/db`                  | Нет         | Проверка соединения с PostgreSQL.                                         |
| `POST`   | `/api/auth/register`          | Нет         | Регистрация по email, паролю и отображаемому имени; создаёт сессию.       |
| `POST`   | `/api/auth/login`             | Нет         | Вход по email и паролю.                                                   |
| `POST`   | `/api/auth/logout`            | Да          | Отзыв текущей сессии и очистка cookie.                                    |
| `GET`    | `/api/auth/me`                | Да          | Получение публичных данных текущего пользователя.                         |
| `GET`    | `/api/auth/providers`         | Нет         | Список настроенных OAuth-провайдеров без раскрытия секретов.              |
| `GET`    | `/api/auth/google`            | Нет         | Начало Google OAuth.                                                      |
| `GET`    | `/api/auth/google/callback`   | OAuth state | Завершение Google OAuth.                                                  |
| `GET`    | `/api/auth/yandex`            | Нет         | Начало Yandex ID OAuth.                                                   |
| `GET`    | `/api/auth/yandex/callback`   | OAuth state | Завершение Yandex ID OAuth.                                               |
| `GET`    | `/api/users/me`               | Да          | Чтение текущего профиля.                                                  |
| `PATCH`  | `/api/users/me`               | Да          | Обновление отображаемого имени и/или HTTPS URL аватара.                   |
| `POST`   | `/api/chats`                  | Да          | Создание чата; заголовок необязателен.                                    |
| `GET`    | `/api/chats`                  | Да          | Список чатов пользователя; `limit` от 1 до 100, по умолчанию 50.          |
| `GET`    | `/api/chats/:chatId`          | Да          | Чтение принадлежащего пользователю чата.                                  |
| `PATCH`  | `/api/chats/:chatId`          | Да          | Переименование принадлежащего пользователю чата.                          |
| `DELETE` | `/api/chats/:chatId`          | Да          | Удаление принадлежащего пользователю чата и его сообщений.                |
| `POST`   | `/api/chats/:chatId/messages` | Да          | Сохранение только пользовательского сообщения.                            |
| `GET`    | `/api/chats/:chatId/messages` | Да          | Список сообщений собственного чата; `limit` от 1 до 100, по умолчанию 50. |
| `POST`   | `/api/ai/chat`                | Да          | Генерация ответа локальной моделью и возврат использованных источников.   |

Параметры запросов:

- Тело регистрации: `email`, `password` (12–128 символов), `displayName` (1–80 символов).
- Тело входа: `email` и `password`.
- Обновление профиля: `displayName` и/или `avatarUrl`; URL аватара должен использовать HTTPS. Требуется хотя бы одно поле.
- Создание чата принимает необязательный `title` (1–200 символов); переименование требует `title`.
- Создание сообщения требует `role: "user"` и непустой `content` длиной до 100 000 символов. Роли `assistant` и `system`, переданные клиентом, отклоняются.
- AI-запрос принимает `chatId` (UUID) принадлежащего пользователю чата и `message` длиной до 12 000 символов; ответ содержит `content` и массив `sources`.
- Генерация сохраняет сообщения пользователя и помощника в чате. Источники ответа сохраняются в столбце JSONB `sources`.

Чтение и изменение чатов ограничено их владельцем. Чужой чат возвращается как не найденный. При удалении чата его сообщения удаляются согласно внешнему ключу базы данных.

В режиме разработки документация API доступна по адресу `http://localhost:3001/docs`, OpenAPI — `http://localhost:3001/openapi.json`. Вне режима разработки обе точки отключены.

## Авторизация и безопасность

- Пароли хешируются Argon2id. При входе неизвестный email не отличается в ошибке от неправильного пароля.
- Токены сессий случайные и непрозрачные. PostgreSQL хранит только HMAC-хеш; срок действия проверяется сервером, а logout отзывает сессию.
- Cookie сессии имеет флаги `HttpOnly`, `SameSite=Lax`, область `Path=/api` и срок действия серверной сессии; `Secure` включается при `NODE_ENV=production`.
- CORS использует точные разрешённые источники с передачей cookie; запросы с недоверенным `Origin` отклоняются.
- Helmet устанавливает защитные HTTP-заголовки. Размер JSON, частота запросов, тела, параметры пути и query-параметры ограничены или проверяются.
- OAuth state сверяется с краткоживущей HTTP-only cookie.
- Ошибки не раскрывают стек вызовов или параметры подключения к базе. В журналы запросов не попадают тела, query-строки, cookie, пароли, коды OAuth и токены.
- Порт PostgreSQL из Compose по умолчанию доступен только на localhost.

Перед production настройте HTTPS, уникальный секрет с высокой энтропией из защищённого хранилища, точные доверенные источники, защиту сети и реквизитов PostgreSQL, а также проверенные процедуры резервного копирования и хранения данных. CSRF-защита основана на `SameSite=Lax` и backend-проверке Origin; сохраняйте оба механизма при изменении схемы браузерного развёртывания.

## AI Runtime и получение знаний

При первом авторизованном запросе backend запускает существующий `../MiryoLove AI/miryolove_ai.py` как постоянный Python-процесс. Готовая модель загружается один раз из `/mnt/Tears/MiryoLove AI/Qwen/miryo_merged_7b`; генерация выполняется последовательно. Интерпретатор, скрипт, путь модели и тайм-аут задаются переменными `AI_RUNTIME_*` и `MIRYO_MODEL_PATH`. Runtime не запускается вместе с backend; первая генерация может ждать несколько минут, пока модель загрузится. Существующий скрипт не поддерживает потоковую генерацию токенов.

AI-сервис проверяет владельца чата и получает до 32 последних сообщений. Runtime токенизирует весь prompt с шаблоном диалога, использует ограничение из конфигурации модели 32 768 токенов (tokenizer указывает 131 072, но это не предел модели), сначала удаляет старую историю, затем сокращает или исключает фрагменты источников, сохраняя место для настроенного ответа. Текущий вопрос добавляется в контекст один раз. Генерация использует EOS ID модели и inference mode; temperature, top-p, sampling, repetition penalty и лимиты настраиваются через переменные окружения.

Ассистент отвечает на общие вопросы, а также помогает с программированием, Linux, базами данных, наукой, историей, переводом, обучением и обсуждением проектов. Язык ответа определяется по текущему сообщению: русский или английский. Поиск выполняется только для явных запросов на источники или актуальные сведения; заголовки статей должны совпадать минимум с 80% очищенных слов запроса. В prompt попадают только релевантные ограниченные фрагменты. Если источник недоступен или не найден, модель отвечает без него и не заявляет о ссылках. Источники возвращаются только если их текст остался в итоговом prompt.

Endpoint `/api/auth/cookie-policy` сообщает фактические имена, содержимое, флаги, область хоста, пути и сроки хранения сессионной и временных OAuth-cookie, а также наличие аналитических или рекламных cookie. На вопросы о cookies runtime отвечает на основе этих данных сервера, а не предположений.

Аддитивная миграция `20261101190000_add_message_sources` добавляет nullable JSONB-столбец. Применяйте её командой `npm run db:deploy`, предварительно проверив `DATABASE_URL`. OAuth работает только при настройке серверных client credentials и callback URL. Инструкции запуска сайта и Caddy находятся в `../MiryoLove AI Web/README.md`.

Runtime не предоставляет модели инструменты, произвольный SQL или доступ к файловой системе. Сброс пароля и потоковая генерация не реализованы, поскольку их нет в текущем API backend и модели.
