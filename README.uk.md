# MiryoLove Server

MiryoLove Server — серверна частина та основа REST API екосистеми MiryoLove. Реалізовано реєстрацію та вхід, серверні сесії, профілі, чати, повідомлення, PostgreSQL, необов’язкову авторизацію Google/Yandex і захищений AI endpoint.

Сайт розміщений в окремому проєкті `../MiryoLove AI Web`. Після першого авторизованого запиту сервер запускає наявний Python-скрипт із моделлю як постійний локальний runtime.

## Продукти та мовна політика

Це окремі продукти:

- **MiryoLove Server** — цей сервер і REST API.
- **MiryoLove AI Web** — окремий браузерний застосунок RU/EN.
- **MiryoLove AI** — наявна Python-логіка та готові ваги в окремих каталогах.
- **MiryoLove Training** — майбутня система навчання моделей, що не входить до цього проєкту.

Англійську мову заплановано як основну мову проєкту (для розробки та інтерфейсу). Російська та українська є додатковими мовами інтерфейсу. Основна мова технічної документації — англійська. Поточний API поки не зберігає бажану локаль і не локалізує тексти відповідей.

## Архітектура

```text
MiryoLove AI Web
        | HTTPS / REST API із сесійною cookie
        v
MiryoLove Server
        +---- Маршрути та контролери Express
        +---- Контракти сервісів авторизації, профілю, чатів, OAuth і ШІ
        +---- PostgreSQL через Prisma
        +---- Google OAuth 2.0 / Yandex ID (необов’язково)
        +---- Постійний Python AI Runtime (наявний скрипт і модель)
        +---- MiryoWiki MediaWiki API та пошук у російській/англійській Wikipedia
```

HTTP-рівень поділено на маршрути, контролери, схеми Zod, middleware і сервіси. Prisma підключається до PostgreSQL. Runtime запускається за першим запитом і завантажує модель один раз; запити генерації обробляються послідовно. Наявний Python-скрипт шукає в MiryoWiki та Wikipedia мовою запитання лише для явних енциклопедичних запитів. Джерела зберігаються разом із відповідями.

## Реалізовані можливості

- Реєстрація та вхід за email і паролем; паролі хешуються за допомогою Argon2id.
- Непрозорі серверні сесії в PostgreSQL; браузер отримує HTTP-only cookie.
- Отримання поточного користувача, читання й оновлення профілю.
- Створення, перегляд списку, читання, перейменування та видалення власних чатів.
- Створення та перегляд повідомлень у чаті, що належить користувачу.
- Необов’язкова авторизація OAuth через Google і Yandex за кодом авторизації.
- Авторизований AI-чат із готовою моделлю та збереженням історії.
- Пошук MiryoWiki/Wikipedia і збереження посилань, якщо текст джерела передано моделі.
- Посилання на джерела повідомлень у nullable JSONB PostgreSQL.
- Перевірки доступності, валідація запитів, JSON-помилки, журналювання запитів, обмеження частоти запитів і OpenAPI/Swagger у режимі розробки.

Публічний маршрут створення повідомлення приймає лише роль `user`. Повідомлення `assistant` і `system` створюються тільки довіреним серверним кодом. AI endpoint зберігає повідомлення користувача й помічника після успішної генерації.

## Технології

- Node.js 20.19 або новіший; рекомендовано Node.js 22 або новішу LTS-версію.
- TypeScript у строгому режимі та Express 5.
- PostgreSQL 17 і Prisma ORM 7.
- Zod, Argon2id, `cookie` та непрозорі серверні сесії з HMAC-хешуванням.
- Необов’язкові Google OAuth 2.0 і Yandex ID OAuth.
- Pino, Helmet, CORS із точною перевіркою джерела та обмеження частоти запитів для маршрутів.
- Vitest, Supertest, ESLint і Prettier.
- Swagger UI за `/docs` і JSON OpenAPI за `/openapi.json` лише в режимі розробки.

## Вимоги

- Node.js 20.19+ і npm.
- PostgreSQL 17: локально або через Docker Compose.
- Docker Compose необов’язковий, якщо PostgreSQL вже доступний окремо.

## Встановлення та змінні середовища

З кореня проєкту:

```sh
npm install
```

Для нового клонування скопіюйте приклад файла середовища лише тоді, коли локального `.env` ще немає:

```sh
cp -n .env.example .env
```

Якщо `.env` уже існує, збережіть його значення та за потреби змінюйте вручну. Не перезаписуйте робочу конфігурацію без перевірки. `.env` виключений із Git; `.env.example` — це шаблон, який не повинен містити реальних облікових даних.

## PostgreSQL через Docker Compose

Конфігурація Compose запускає лише PostgreSQL. Дані зберігаються в іменованому томі `miryolove-postgres-data`; типово порт публікується лише на `127.0.0.1`.

```sh
docker compose up -d
docker compose ps
```

Налаштування Compose можна передавати через середовище. Якщо параметри PostgreSQL змінено, переконайтеся, що `DATABASE_URL` вказує на ті самі хост, порт, базу та користувача. Не відкривайте облікові дані розробки для доступу з публічної мережі.

Зупинити сервіс, зберігши іменований том із даними:

```sh
docker compose down
```

Не видаляйте том і не редагуйте `postgres-data/` під час звичайного очищення. Деструктивні операції з базою або томом потребують явного рішення щодо збереження даних і перевіреної резервної копії.

## Prisma та міграції

Згенерувати Prisma Client:

```sh
npm run db:generate
```

Для розробки міграцій передбачено команду:

```sh
npm run db:migrate
```

Для застосування перевірених міграцій до цільової бази:

```sh
npm run db:deploy
```

`db:migrate` і `db:deploy` підключаються до бази з `DATABASE_URL` і можуть змінити її схему. Перед запуском перевірте цільове середовище. Не використовуйте production- або користувацьку базу для експериментів. Нові міграції спочатку перевіряйте на окремій тимчасовій базі PostgreSQL.

Інша доступна команда Prisma:

```sh
npm run db:studio
```

Схема описує користувачів, OAuth-акаунти, сесії, чати й повідомлення. Використовуються UUID, унікальні обмеження для email та акаунтів провайдерів, зовнішні ключі з каскадною поведінкою, переліки PostgreSQL та індекси для строку дії сесій, списків чатів і повідомлень. Хеші паролів і вихідні токени сесій не повертаються API; у базі зберігається лише HMAC-хеш випадкового токена сесії.

## Запуск і збірка

Запустити сервер розробки зі спостереженням за файлами:

```sh
npm run dev
```

Зібрати проєкт (згенерувати Prisma Client і скомпілювати TypeScript), потім запустити зібраний сервер:

```sh
npm run build
npm start
```

Застосунок слухає порт із `PORT` (типово `3001`). `/health` повертає стан сервісу. `/health/db` перевіряє PostgreSQL і повертає узагальнену помилку недоступності, якщо база недосяжна. Сервер не застосовує міграції автоматично під час запуску.

## Тести та якість коду

```sh
npm test
npm run lint
npm run format:check
```

`npm test` запускає набір Vitest. HTTP-тести використовують in-memory doubles сервісів для перевірки авторизації, валідації, прав власності, OAuth state та обробки помилок; хешування паролів тестується окремо. Також доступна перевірка схеми Prisma:

```sh
npx prisma validate
```

Перевірити конфігурацію Compose без запуску сервісів можна командою:

```sh
docker compose config --quiet
```

Для інтеграційних перевірок бази використовуйте окремий тимчасовий PostgreSQL і спеціальний тестовий `DATABASE_URL`; не спрямовуйте тестові команди на користувацьку базу.

## Налаштування OAuth (необов’язково)

Вхід за email і паролем працює без OAuth. Конфігурація OAuth необов’язкова. Не додавайте секрети клієнта до системи контролю версій.

### Google

1. Створіть OAuth 2.0 Web client і налаштуйте екран згоди.
2. Для локальної розробки зареєструйте URI перенаправлення `http://localhost:3001/api/auth/google/callback`.
3. Задайте `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` і `GOOGLE_CALLBACK_URL` у локальному середовищі.
4. Почніть потік запитом `GET /api/auth/google`.

Сервер використовує потік authorization code з областями `openid email profile`, звіряє випадкове значення state з короткочасною HTTP-only cookie та вимагає підтверджену адресу Google. Токени доступу провайдера не зберігаються.

### Yandex ID

1. Зареєструйте OAuth-застосунок у Yandex ID.
2. Для локальної розробки додайте callback `http://localhost:3001/api/auth/yandex/callback`.
3. Задайте `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET` і `YANDEX_CALLBACK_URL` у локальному середовищі.
4. Почніть потік запитом `GET /api/auth/yandex`.

Сервер обмінює код авторизації на дані профілю провайдера та використовує такий самий захист state-cookie. Токени доступу провайдера не зберігаються. Помилки провайдера й конфігурації журналюються без кодів авторизації, значень state, секретів клієнта й токенів доступу.

Якщо адреса провайдера вже належить наявному акаунту, сервер повертає `ACCOUNT_LINKING_REQUIRED` і не об’єднує акаунти автоматично. Авторизоване прив’язування та від’єднання провайдерів не реалізовано.

## REST API

Усі JSON-помилки мають таку форму:

```json
{ "error": { "code": "ERROR_CODE", "message": "Повідомлення для користувача." } }
```

Захищені маршрути використовують HTTP-only cookie `miryolove_session`. Сервер не видає фронтенду bearer-токен. Для браузерних запитів передавайте cookie та використовуйте дозволений Origin.

| Метод    | Шлях                          | Авторизація | Призначення                                                              |
| -------- | ----------------------------- | ----------- | ------------------------------------------------------------------------ |
| `GET`    | `/health`                     | Ні          | Стан сервісу.                                                            |
| `GET`    | `/health/db`                  | Ні          | Перевірка з’єднання з PostgreSQL.                                        |
| `POST`   | `/api/auth/register`          | Ні          | Реєстрація за email, паролем і відображуваним ім’ям; створює сесію.      |
| `POST`   | `/api/auth/login`             | Ні          | Вхід за email і паролем.                                                 |
| `POST`   | `/api/auth/logout`            | Так         | Відкликання поточної сесії та очищення cookie.                           |
| `GET`    | `/api/auth/me`                | Так         | Отримання публічних даних поточного користувача.                         |
| `GET`    | `/api/auth/providers`         | Ні          | Список налаштованих OAuth-провайдерів без розкриття секретів.            |
| `GET`    | `/api/auth/google`            | Ні          | Початок Google OAuth.                                                    |
| `GET`    | `/api/auth/google/callback`   | OAuth state | Завершення Google OAuth.                                                 |
| `GET`    | `/api/auth/yandex`            | Ні          | Початок Yandex ID OAuth.                                                 |
| `GET`    | `/api/auth/yandex/callback`   | OAuth state | Завершення Yandex ID OAuth.                                              |
| `GET`    | `/api/users/me`               | Так         | Читання поточного профілю.                                               |
| `PATCH`  | `/api/users/me`               | Так         | Оновлення відображуваного імені та/або HTTPS URL аватара.                |
| `POST`   | `/api/chats`                  | Так         | Створення чату; заголовок необов’язковий.                                |
| `GET`    | `/api/chats`                  | Так         | Список чатів користувача; `limit` від 1 до 100, типово 50.               |
| `GET`    | `/api/chats/:chatId`          | Так         | Читання чату, що належить користувачу.                                   |
| `PATCH`  | `/api/chats/:chatId`          | Так         | Перейменування власного чату.                                            |
| `DELETE` | `/api/chats/:chatId`          | Так         | Видалення власного чату та його повідомлень.                             |
| `POST`   | `/api/chats/:chatId/messages` | Так         | Збереження лише повідомлення користувача.                                |
| `GET`    | `/api/chats/:chatId/messages` | Так         | Список повідомлень власного чату; `limit` від 1 до 100, типово 50.       |
| `POST`   | `/api/ai/chat`                | Так         | Генерація відповіді локальною моделлю та повернення використаних джерел. |

Параметри запитів:

- Тіло реєстрації: `email`, `password` (12–128 символів) і `displayName` (1–80 символів).
- Тіло входу: `email` і `password`.
- Оновлення профілю: `displayName` та/або `avatarUrl`; URL аватара має використовувати HTTPS. Потрібне принаймні одне поле.
- Створення чату приймає необов’язковий `title` (1–200 символів); для перейменування `title` обов’язковий.
- Створення повідомлення потребує `role: "user"` і непорожній `content` довжиною до 100 000 символів. Ролі `assistant` і `system`, надіслані клієнтом, відхиляються.
- Запит ШІ приймає `chatId` (UUID) чату користувача та `message` довжиною до 12 000 символів; відповідь містить `content` і масив `sources`.
- Генерація зберігає повідомлення користувача й помічника в чаті. Джерела відповіді зберігаються у стовпці JSONB `sources`.

Читання та зміна чатів обмежені їхнім власником. Чужий чат повертається як не знайдений. Під час видалення чату його повідомлення видаляються відповідно до зовнішнього ключа бази даних.

У режимі розробки документація API доступна за адресою `http://localhost:3001/docs`, OpenAPI — `http://localhost:3001/openapi.json`. Поза режимом розробки обидві точки вимкнені.

## Авторизація та безпека

- Паролі хешуються Argon2id. Під час входу невідомий email не відрізняється в помилці від неправильного пароля.
- Токени сесій випадкові й непрозорі. PostgreSQL зберігає лише HMAC-хеш; строк дії перевіряється сервером, а logout відкликає сесію.
- Cookie сесії має прапорці `HttpOnly` і `SameSite=Lax`; `Secure` вмикається за `NODE_ENV=production`.
- CORS використовує точні дозволені джерела з передаванням cookie; запити з недовіреним `Origin` відхиляються.
- Helmet додає захисні HTTP-заголовки. Розмір JSON, частота запитів, тіла, параметри шляху й query-параметри обмежуються або перевіряються.
- OAuth state звіряється з короткочасною HTTP-only cookie.
- Помилки не повертають stack trace або параметри підключення до бази. У журнали запитів не потрапляють тіла, query-рядки, cookie, паролі, OAuth-коди й токени.
- Порт PostgreSQL із Compose типово доступний лише на localhost.

Перед production налаштуйте HTTPS, унікальний секрет із високою ентропією у захищеному сховищі, точні довірені джерела, захист мережі й облікових даних PostgreSQL, а також перевірені процедури резервного копіювання та зберігання даних. Оцініть CSRF-захист з урахуванням остаточної схеми браузерного розгортання; не послаблюйте `SameSite=Lax` і перевірку Origin.

## AI Runtime і отримання знань

Після першого авторизованого запиту backend запускає наявний `../MiryoLove AI/miryolove_ai.py` як постійний Python-процес. Готова модель завантажується один раз із `/mnt/Tears/MiryoLove AI/Qwen/miryo_merged_7b`; запити генерації обробляються послідовно. Інтерпретатор, скрипт, шлях моделі й тайм-аут задаються змінними `AI_RUNTIME_*` та `MIRYO_MODEL_PATH`. Runtime не запускається під час старту backend; перший запит може чекати кілька хвилин на завантаження моделі. Наявний скрипт не підтримує потокову генерацію токенів.

AI-сервіс перевіряє власника чату до завантаження історії. Зовнішній пошук виконується лише для явних енциклопедичних запитів або актуальних відомостей. Використовуються функції пошуку статей у наявному Python-скрипті; перевіряються MiryoWiki та Wikipedia мовою запитання, а моделі передається обмежений фрагмент статті з її джерелом. До публічних API надсилається лише очищена пошукова фраза, а не історія повідомлень чи дані акаунта. Якщо джерело недоступне або статтю не знайдено, модель відповідає без нього. Повертаються й зберігаються лише джерела, текст яких передано в контекст моделі.

Адитивна міграція `20261101190000_add_message_sources` додає nullable JSONB-стовпець. Застосуйте її командою `npm run db:deploy`, попередньо перевіривши `DATABASE_URL`. OAuth працює лише після налаштування серверних client credentials і callback URL. Інструкції запуску сайту та Caddy наведено в `../MiryoLove AI Web/README.md`.

Runtime не надає моделі інструменти, довільний SQL або доступ до файлової системи. Скидання пароля й потокова генерація не реалізовані, оскільки їх немає в поточному API backend і моделі.

## Структура проєкту

```text
src/
  config/        Змінні середовища, журнал, клієнт Prisma
  controllers/   HTTP-обробники запитів
  docs/          Документ OpenAPI
  middleware/    Авторизація, обмеження частоти, помилки, журналювання
  routes/        Маршрути авторизації, профілю та чатів
  schemas/       Схеми запитів Zod
  services/      Авторизація, OAuth, профіль, чати, межа ШІ
  types/         Контракти сервісів і розширення типів Express
  utils/         Cookie, помилки, валідація, хешування паролів
  app.ts         Складання застосунку Express
  server.ts      Життєвий цикл HTTP і перевірка PostgreSQL
prisma/
  schema.prisma
  migrations/
tests/
```
