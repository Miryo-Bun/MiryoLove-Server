# Полный аудит MiryoLove Server: персональные данные и 152-ФЗ

**Дата аудита:** 4 ноября 2026 г.
**Версия репозитория:** `c3c0cacb5246a2fd69c0cf2f28c80a8b2992be22` (`feature/miryolove-ai-runtime-oauth-ui`).
**Объект:** рабочая копия MiryoLove Server, включая незакоммиченные изменения, существующую локальную PostgreSQL и backup-скрипт.
**Назначение документа:** технический аудит готовности и перечень вопросов для оператора/юриста. Не является юридическим заключением.

## A. Общая оценка

### Объём и методы

Проверены `src/`, Prisma schema и миграции, `tests/`, `app.py`, Compose, шаблон `.env.example`, README на двух языках, `docs/`, `scripts/backup.sh`, зависимости и тесты. В PostgreSQL выполнялись только read-only запросы системных метаданных: настройки сервера, роли, grants и правила `pg_hba`; пользовательские строки не читались. `.env` и passphrase не раскрывались. Проверены Git status/history для `.env`, права файлов, Compose bindings и сведения о backup.

Рабочее дерево содержит многочисленные незакоммиченные изменения, включая добавленный маршрут удаления аккаунта, обновления зависимостей, документацию и backup-скрипт. Поэтому результаты относятся к **текущему содержимому рабочей копии**, но не доказывают, что эти изменения закоммичены или развёрнуты. Текущий `HEAD` — указанный выше commit; состояние работающего приложения/его версии не подтверждено.

Проверки в рабочей копии: `npm test` — 18 тестов успешно; `npm audit` — 0 advisories; `npm run build`, `npm run lint`, форматирование и `npx prisma validate` ранее завершались успешно. Compose-конфигурация проверялась с временно переданным непроизводственным значением; обычная проверка текущего Compose без `POSTGRES_PASSWORD` завершается ошибкой. Ни миграции, ни изменения PostgreSQL, ни перезапуск контейнера при этом аудите не выполнялись.

### Ограничения

- Официальный портал правовой информации не загрузился (TLS-соединение завершается ошибкой); страницы Роскомнадзора вернули 403. Поэтому действующая на 04.11.2026 консолидированная редакция нормативных текстов и подзаконных актов **не была независимо сверена**. Ниже приводятся релевантные реквизиты/статьи для правовой сверки, а не утверждение о подтверждённом текущем содержании каждой нормы.
- Репозиторий не устанавливает личность оператора, субъектов, оснований обработки, число пользователей, место физического размещения оборудования, условия договоров или факт уведомления Роскомнадзора.
- Не проверялись внешние frontend, хостинг, reverse proxy/Caddy, DNS, firewall, административные учётные записи ОС, удалённые журналы, договоры с провайдерами и содержимое внешнего AI runtime/модели.
- На хосте при проверке слушал только опубликованный PostgreSQL `127.0.0.1:5432`; API на `3001` и legacy FastAPI на `8000` в списке слушающих сокетов не обнаружены. Это моментальный снимок, не доказательство отсутствия других deployment-узлов или внешнего proxy.
- Пользовательский контент свободной формы может содержать сведения специальных категорий или биометрические данные, даже если схема не имеет отдельных полей для них.

## C. Найденные проблемы

Приоритет обозначает порядок исправления для проекта, а не формальную степень нарушения закона. Проблемы ниже фиксируют исходный read-only снимок; последующие исправления и их ограничения перечислены в разделе I.

### F-01 — Избыточные привилегии runtime-роли PostgreSQL

- **Приоритет:** высокий.
- **Доказательства:** проверка `pg_roles` показала для роли подключения `rolsuper=true`, `rolcreatedb=true`, `rolcreaterole=true`; в grants присутствуют `TRUNCATE`, `REFERENCES`, `TRIGGER` и CRUD. PostgreSQL 17.11, `ssl=off`.
- **Данные/последствия:** все аккаунты, сессии, переписки и связанные записи доступны этому principal; компрометация приложения может стать компрометацией всего кластера/удалением данных.
- **Основание:** 152-ФЗ ст. 7, 19; ПП РФ №1119 и приказ ФСТЭК №21 — точная применимость/меры требуют модели угроз и актуальной правовой сверки.
- **Рекомендация:** отдельные runtime, migration и admin роли; runtime оставить только необходимые DML-права на нужные объекты. Проверить политику TLS, доступы, восстановление и переключение на staging; не отзывать права текущей рабочей роли без проверенного перехода и отката.

### F-02 — Параллельный legacy FastAPI endpoint без аутентификации

- **Приоритет:** высокий, если endpoint развёрнут или опубликован; средний в текущем снимке.
- **Доказательства:** [app.py](../app.py) определяет `POST /api/chat` без auth middleware, без rate limit и без ограничения длины сообщения; `user_id` из body не подтверждает личность. Файл не входит в Compose, а порт `8000` на хосте при проверке не слушал. `python app.py` привязывает его к loopback, но запуск ASGI-командой может задать внешний bind самостоятельно.
- **Данные/последствия:** неаутентифицированный доступ к затратной генерации; произвольный пользовательский текст может включаться в запрос к Wikipedia. Возникает второй, отличающийся от основного API путь обработки.
- **Основание:** безопасность/конфиденциальность и минимизация — 152-ФЗ ст. 5, 7, 19; актуальную применимость требований проверить.
- **Рекомендация:** установить deployment-статус; не публиковать endpoint. До любого использования как сервиса закрыть аутентификацию, авторизацию, rate/size/time limits и сетевой egress; предпочтительно убрать его из production deployment, если он legacy.

### F-03 — Фактическая передача пользовательского текста стороннему поисковому endpoint

- **Приоритет:** высокий до подтверждения целей, оснований, получателей и локализации.
- **Доказательства:** в `app.py` полное `request.message` передаётся в `fetch_wikipedia_summary`, кодируется в URL-параметр `srsearch` и отправляется `urllib.request.urlopen` на `https://{lang}.wikipedia.org`. Условия запуска — trigger phrase и `use_wiki=true`, значение по умолчанию true. В OAuth-сервисе имеются фиксированные HTTPS вызовы к Google/Yandex для обмена code и получения profile. Код и удалённая система не устанавливают договоры, срок хранения и регион данных.
- **Данные/последствия:** пользователь может включить в вопрос email, имя, содержание переписки или иные ПД; поисковые запросы могут оказаться у внешнего оператора и попасть в URL-логи. Страны обработки и возможная трансграничная передача не установлены. Для основного Python runtime вне этой рабочей директории полный сетевой поток не проверен.
- **Основание:** 152-ФЗ ст. 5–7, 12, 18(5); необходимость локализации, отдельного уведомления и/или иных условий зависит от субъектов, стран, исключений и актуальной редакции. Юридическая сверка обязательна.
- **Рекомендация:** инвентаризировать egress и обработчиков; минимизировать/редактировать поисковую фразу, исключить переписку и идентификаторы; до отправки определить цель, основание, уведомления, договоры, регионы и пользовательское информирование. Не считать локальную модель гарантией локальной обработки, пока не проверены retrieval и telemetry.

### F-04 — Не установлена локализация баз, резервов и внешних компонентов

- **Приоритет:** высокий до начала/продолжения обработки данных российских граждан.
- **Доказательства:** обнаружен локальный Docker named volume, Docker bridge IP и host binding на loopback. Физический дата-центр/страна не устанавливается этими признаками. Указаны внешние OAuth endpoints и wiki/Wikipedia endpoints. Единственная найденная зашифрованная backup-копия расположена на файловой системе того же проекта/хоста.
- **Последствия:** нельзя подтвердить выполнение локализации или оценить передачу; backup также содержит базу с пользовательскими данными.
- **Основание:** 152-ФЗ ст. 18(5), 12, поправки 242-ФЗ и 23-ФЗ; актуальную редакцию и исключения проверить.
- **Рекомендация:** получить письменные сведения о площадках, регионах, резервировании, обработчиках, репликациях и egress; сопоставить все требуемые операции с фактическим местом первичной записи и дальнейшей обработки.

### F-05 — Пользовательские UUID попадают в HTTP-журнал

- **Приоритет:** средний.
- **Доказательства:** исходный снимок middleware писал `request.path`; маршруты чатов содержат `:chatId` в path. В последующем изменении заменено на route template и random request ID (см. раздел I). Логи идут в stdout; внешняя ротация/retention/access-control не установлены.
- **Данные/последствия:** косвенный идентификатор и история обращения могут сохраняться после удаления аккаунта/чата; содержание сообщений не журналируется middleware.
- **Основание:** 152-ФЗ ст. 5, 7, 19, 21 — в контексте возможности сопоставить UUID с записью пользователя.
- **Рекомендация:** журналировать шаблон маршрута без path-параметров или структурированный route name; установить срок, доступ, ротацию и процедуру incident hold для всех принимающих stdout сервисов.

### F-06 — Хранение пользователя в backup не синхронизировано с удалением

- **Приоритет:** высокий организационно/средний технически.
- **Доказательства:** `DELETE /api/users/me` полагается на FK cascade, но не изменяет существующие шифрованные дампы. В последующем изменении автоматическое удаление backup выключено; расписание не установлено. Найденный архив и passphrase находятся на том же хосте.
- **Данные/последствия:** удалённая основная запись может оставаться в архиве до его ротации; компрометация хоста может затронуть и копию, и ключ. Нет утверждённого максимального срока хранения/удаления и независимой off-host копии.
- **Основание:** 152-ФЗ ст. 5, 19, 21; точные правила хранения и уничтожения зависят от цели и юридических исключений.
- **Рекомендация:** утвердить retention для backup и порядок исполнения удаления с учётом архивов; отдельно контролировать ключ и архивы; документировать исключения/срок истечения копий. Не обещать безусловное удаление до этого решения.

### F-07 — Account-delete endpoint не очищает cookie и не реализует процесс обращения субъекта

- **Приоритет:** средний.
- **Доказательства:** [users.routes.ts](../src/routes/users.routes.ts) предоставляет `DELETE /me` после `requireAuth`; исходный снимок отвечал `204` без `clearSessionCookie`. Последующее изменение очищает cookie при успешном удалении; service удаляет account, sessions, chats, messages, OAuth каскадом. Нет re-auth/явного подтверждения, экспорта или процесса проверки личности для запросов вне активной сессии. Deployment не доказан.
- **Данные/последствия:** cookie остаётся в браузере до expiry, хотя серверная запись уже отозвана; удаление основной БД не обрабатывает логи/backups/external processors. Имеющийся endpoint не реализует все возможные права субъекта и юридические исключения.
- **Основание:** 152-ФЗ ст. 14, 20, 21 — действующие сроки/процедуры проверить по текущей редакции.
- **Рекомендация:** после подтверждённого процесса очищать cookie на ответе, определить повторную аутентификацию/подтверждение и оформить workflow: запрос, проверка, решение, исполнение, исключения, уведомление и учёт копий.

### F-08 — Compose-конфигурация сейчас невалидна без новой DB-переменной

- **Приоритет:** средний (эксплуатационный).
- **Доказательства:** текущий `docker-compose.yml` требует `${POSTGRES_PASSWORD:?...}`, но проверка имён переменных текущего `.env` не обнаружила `POSTGRES_PASSWORD`; `docker compose config --quiet` без неё завершился ошибкой. Работающий container при этом оставался healthy и не перезапускался; новый Compose-файл не был применён.
- **Затрагиваемые данные:** непосредственно строки субъектов не меняются; затрагиваются DB credentials и доступность воспроизводимого развертывания.
- **Последствия:** оператор не сможет валидировать/воспроизвести Compose deployment в текущем окружении; небезопасное быстрое исправление может привести к рассинхронизации пароля приложения и уже созданного DB volume.
- **Основание:** прямого отдельного требования 152-ФЗ к Compose-переменной не устанавливается; влияние на доступность/защиту должно учитываться в технической оценке мер по ст. 19, если применимо.
- **Рекомендация:** отдельно согласовать с DBA способ задать/сопоставить существующий credential без вывода в shell/history; не менять пароль volume простой правкой `.env`; затем проверить Compose без перезапуска production.

### F-09 — Секрет сессии: production-проверка ограничена сравнением строк

- **Приоритет:** средний.
- **Доказательства:** [env.ts](../src/config/env.ts) имеет development fallback и в production отвергает несколько известных placeholder values, но принимает любую иную строку длиной от 32 символов. Случайность/энтропия не валидируется самим кодом. Состояние `NODE_ENV`/secret не включено в отчёт.
- **Затрагиваемые данные:** сессионная аутентификация аккаунтов; в таблице хранится HMAC hash session token.
- **Последствия:** предсказуемый, но достаточно длинный ключ может позволить подделку HMAC для session token hash при иных условиях компрометации.
- **Основание:** меры защиты и сохранение конфиденциальности, 152-ФЗ ст. 19, если применимо к определённой ИСПДн.
- **Рекомендация:** задать уникальный криптографически случайный секрет в production через защищённое хранилище/процедуру; проверять конфигурацию при deploy. Не менять текущий ключ автоматически без оценки отзыва всех сессий.

### F-10 — Внешняя граница Express и TLS не подтверждены

- **Приоритет:** высокий до публичной эксплуатации.
- **Доказательства:** `src/server.ts` вызывает `server.listen(env.PORT)` без явного loopback bind; Compose управляет только PostgreSQL и не описывает API ingress, TLS, firewall или reverse proxy. API порт сейчас не слушал на проверенном хосте.
- **Затрагиваемые данные:** учётные данные, session cookies, профиль и пользовательская переписка при сетевой передаче.
- **Последствия:** при прямом запуске на публичной машине Node может слушать на всех интерфейсах; HTTPS и сетевые ограничения нельзя вывести из кода.
- **Основание:** 152-ФЗ ст. 19 — требуемые меры определяются оценкой системы/угроз.
- **Рекомендация:** зафиксировать production deployment topology, TLS termination, firewall, trusted proxies, bind address и health access; проверить фактическую конфигурацию с владельцем инфраструктуры перед запуском.

## E. План дальнейших действий

Предлагаемые шаги — не выполненные изменения. С учётом требований этого аудита, перед любым внедрением требуется отдельное решение владельца.

### 1. Срочные технические проверки

1. До публичного запуска подтвердить, что legacy `/api/chat` не выставлен; определить реальный bind/TLS/firewall для Express.
2. С DBA спланировать runtime/migration/admin DB roles и TLS; сначала тест на staging/восстановленной копии, без отзыва production grants вслепую.
3. Определить data egress для OAuth, main AI runtime и wiki retrieval; минимизировать передачу query/контента.
4. Согласовать корректное безопасное получение Compose password без изменения существующего volume; документировать владельца секрета.
5. Исключить UUID из request logs и утвердить срок/ротацию для stdout/log consumers.
6. Не считать текущий self-delete достаточным для завершения всех обязанностей: определить cookie reset, подтверждение пользователя, workflow обращения и обработку архивов.

### 2. Архитектурные изменения

- Изолировать application DB role от DDL/admin; проверить принцип minimum privilege.
- Зафиксировать единственный производственный API path; не использовать legacy FastAPI как параллельный публичный endpoint без полной auth/abuse защиты.
- Ограничить AI backlog, определить допустимый контекст и сформировать allowlist сетевых получателей.
- Настроить централизованные, ограниченные по сроку и доступу журналы без query/body/path identifiers.
- Утвердить стратегию backup: ключ отдельно от хоста/архивов, проверяемое restore, согласованная ротация и мониторинг. Внешнее/off-host хранение возможно только после отдельного решения и проверки региона/провайдера.

### 3. Организационные меры

- Установить фактического оператора, роли уполномоченных лиц, администраторов и обработчиков.
- Зафиксировать цели, категории субъектов/данных, основания, сроки, получателей, операции и доступы.
- Определить необходимость определения уровня защищённости ИСПДн и модели угроз; после этого назначить применимые меры по текущим нормативам.
- Утвердить процессы обработки запросов субъектов, исключений хранения и контроля удаления.

### 4. Документы и юридические процедуры

- Сверить текущую редакцию 152-ФЗ, 149-ФЗ, поправок 242-ФЗ/23-ФЗ/266-ФЗ и применимых постановлений/приказов по официальным публикациям.
- Проверить необходимость уведомления Роскомнадзора и соответствие фактическому составу обработки; отсутствие сведений в Git не является свидетельством неподачи.
- Подготовить/проверить публичную политику и отдельные согласия там, где они требуются; не придумывать оператора или универсальное согласие.
- Проверить правовые условия для трансграничной передачи и договоров-поручений, включая OAuth и retrieval.
- Актуализировать incident response и проверить сроки/состав сообщения по действующему тексту закона.

### 5. Проверка инфраструктуры и провайдеров

- Получить подтверждённый физический регион основного БД и backup-хранилища; инвентаризировать snapshots, replicas, support access и логи провайдера.
- Получить схему ingress/egress, Caddy/reverse proxy, TLS termination, firewall и адресов API.
- Установить регионы, роли и условия Google/Yandex, MiryoWiki, Wikimedia, хостинга и внешнего AI runtime.
- Проверить внешний frontend на cookies/local storage/analytics/consent и обработку запросов на удаление.

### 6. Повторный аудит

После предоставления owner/legal/infrastructure evidence повторно оценить локализацию, трансграничные передачи, уведомление, уровень ИСПДн, retention, фактическое deployment и тесты удаления/restore. Изменения production — только после отдельного согласования, тестирования и rollback-плана.

## H. Итоговое заключение

Подтверждены отдельные технические контроли: Argon2id, серверные сессии с hash в БД, ограниченные cookies, OAuth state validation, auth/ownership checks в Express, schema validation, rate limiting, общие ошибки, минимизированные request logs, исключение `.env` из Git и успешные тесты/аудит зависимостей в текущей копии. В текущем изменённом рабочем дереве есть каскадное self-delete, encrypted backup script и документы; deployment этих правок не подтверждён.

Остаточные риски: runtime PostgreSQL role — superuser; TLS PostgreSQL выключен; неизвестны физическая локализация и обработчики; legacy FastAPI endpoint не имеет auth, если будет опубликован; пользовательский текст может уйти в внешний поиск; сроки основной БД/логов/backup не утверждены; backup key и архив локальны одному хосту; проверенная `.env` не содержит обязательный для Compose `POSTGRES_PASSWORD`; self-delete не удаляет backups/logs. Исправленные в рабочей копии проблемы UUID в request logs и очистки cookie ещё не подтверждены как развёрнутые.

Из кода и локальной конфигурации нельзя установить, кто является оператором, какие правовые основания действуют, подано ли уведомление, какие документы опубликованы, где физически расположена инфраструктура, какие договоры заключены, какие субъекты/объёмы/угрозы имеют место и какие требования подзаконных актов применимы к определённому уровню ИСПДн.

**Вывод:** текущих доказательств недостаточно, чтобы считать MiryoLove Server соответствующим 152-ФЗ. В рабочей копии исправлены некоторые локальные риски логирования, удаления сессии и неограниченного AI backlog, но production deployment этих изменений не подтверждён. Технический этап готов к следующей проверке владельцем, DBA, инфраструктурным специалистом и юристом после получения ответов на вопросы раздела F. До неё не следует заявлять о соответствии законодательству или переносить неопределённые обработки в production.
