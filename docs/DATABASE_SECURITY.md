# PostgreSQL и Prisma

## Наблюдаемое состояние

- PostgreSQL `17.11`, образ Compose `postgres:17-alpine`, named volume `miryoloveserver_miryolove-postgres-data`.
- Проверенное соединение приходило из Compose bridge; PostgreSQL сообщил `ssl=false`.
- База `miryolove`, роль приложения `miryo_user` имела SUPERUSER, CREATEDB и CREATEROLE. Другая обнаруженная login-role не была superuser. Значения credential не выводились.
- Подключение ORM — Prisma 7 + `@prisma/adapter-pg`; миграции init и nullable `messages.sources` отмечены применёнными.
- Таблицы `users`, `oauth_accounts`, `sessions`, `chats`, `messages`, `_prisma_migrations`; индексы/unique/FK определены в Prisma schema и миграциях.
- В Compose порт БД публикуется на loopback хоста; наружная firewall-конфигурация отдельно не проверена.

## План least-privilege перехода (не применён)

Исходная проблема: фактическая runtime login-role `miryo_user` имеет `SUPERUSER`, `CREATEDB` и `CREATEROLE`; у неё также избыточные права на объекты. Ничего в правах production роли не менялось.

Разделение обязанностей по коду:

- Runtime использует обычные CRUD-операции с профилями, OAuth-записями, сессиями, чатами и сообщениями; приложению не нужны `SUPERUSER`, `CREATEDB` или `CREATEROLE`.
- `prisma migrate deploy` выполняет DDL. В PostgreSQL одного `GRANT` на таблицы недостаточно для `ALTER TABLE`; отдельная migration-role должна быть владельцем мигрируемых объектов/схемы или получать права через контролируемый `SET ROLE`. Миграционная роль не должна использоваться HTTP-сервисом.
- DBA/admin роль используется только человеком/автоматизацией для административного управления.

Предварительный grant matrix для проверки на восстановленной копии (не запускать на production):

| Роль                 | База / схема                                          | Таблицы                                                                               | Последовательности                    | DDL                                    |
| -------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------- | -------------------------------------- |
| `miryo_app_runtime`  | `CONNECT`; `USAGE` на прикладную схему                | `SELECT`, `INSERT`, `UPDATE`, `DELETE` на нужные Prisma-таблицы                       | `USAGE`, `SELECT`                     | Нет                                    |
| `miryo_app_migrator` | `CONNECT`; владение или контролируемые права на схему | Владение объектами, создаваемыми/изменяемыми миграциями, включая `_prisma_migrations` | Владение/DDL для создаваемых sequence | Только во время одобренного deployment |
| DBA                  | Административный доступ по отдельной процедуре        | По необходимости                                                                      | По необходимости                      | Да; не использовать приложением        |

Права следует сузить до таблиц, действительно используемых runtime, после проверки `schema.prisma`, generated SQL всех миграций и запросов приложения. Нельзя полагаться на потенциальный `TRUNCATE`, `CREATE`, `REFERENCES` или `TRIGGER` для runtime без доказанной необходимости. Настроить default privileges для объектов, создаваемых migration owner, и проверить ownership типов/enum, sequence и `_prisma_migrations`.

### План безопасного перехода и отката

1. DBA получает одобренное окно и проверенный зашифрованный backup; восстановить его в изолированную тестовую БД. Снять read-only inventory владельцев объектов, grants, схем, sequences, enum/types и миграционной истории, не выгружая пользовательские строки в отчёт.
2. Создать отдельные login roles с `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION`; секреты передать через штатное хранилище секретов, не через Git/логи/отчёт.
3. На восстановленной БД выдать runtime только требуемые grants и прогнать регистрацию, OAuth linkage, login/logout, профиль, чат CRUD, сообщения и удаление. Отдельно прогнать `prisma migrate deploy` на disposable clone для migration-role.
4. Проверить read-only/negative cases: runtime не может создавать БД/роль, менять схему, читать неразрешённую схему или выполнять ненужные destructive grants. Проверить текущее и будущее default privileges.
5. Только после письменного одобрения изменить secret/config для нового runtime role в контролируемом deployment, проверить health, user flows и логи. Не выполнять миграцию production вместе с переключением роли.
6. Откат: вернуть прежний `DATABASE_URL`/секрет через штатную конфигурацию, не удалять новые/старые роли и не отзывать старые grants до завершения периода наблюдения. При любом сомнении остановиться, сохранить состояние и привлечь DBA.

Никакие production-роли, пароли, grants, schema ownership или миграции этим планом не меняются.

## TLS для PostgreSQL (план, не включён)

Наблюдаемое состояние: PostgreSQL сообщал `ssl=false`, внутри контейнера слушает `*`; опубликованный host port привязан к `127.0.0.1:5432`, host connections в проверенном `pg_hba.conf` требуют SCRAM, local socket/loopback правила используют `trust`. Это снижает внешнюю доступность, но не шифрует трафик на Docker/loopback границах и не подтверждает защиту от доступа с хоста/соседних контейнеров.

Перед включением подготовить CA и отдельный серверный сертификат с SAN для имени, реально используемого каждым клиентом (например, `postgres` внутри Compose и `localhost`/`127.0.0.1` только если именно так подключается локальный клиент). Закрытый ключ хранить вне Git и image, read-only mount, доступ только PostgreSQL OS user, mode `0600`; сертификат/CA — read-only. Проверить цепочку, hostname, срок и процедуру перекрывающего обновления сертификатов. Не использовать `rejectUnauthorized: false`, `sslmode=require` без проверки hostname/CA или отключение проверки peer.

На disposable clone настроить PostgreSQL `ssl=on`, TLS-only HBA для нужных host clients и `verify-full` с правильной CA/SAN в `pg`/Prisma 7 adapter. Проверить совместимость точной версии `pg`, формат SSL parameters и hostname validation отдельными успешными и отрицательными тестами (неверный CA, hostname, expired cert). Проверить локальный socket отдельно. Только после одобрения подготовить maintenance/rollback план; production Compose, сертификаты, HBA и сервер не менялись.

## Важно

Не понижать права работающей роли напрямую: сервисы могут зависеть от ownership при миграциях, а работа приложения требует тестируемого переключения. Следовать приведённым выше role matrix и rollback plan. Не менять существующую роль/пароль без письменного разрешения.

Compose теперь не подставляет известный пароль по умолчанию. Установите явный случайный POSTGRES_PASSWORD и согласуйте его с фактическим существующим кластером до перезапуска: изменение Compose env не меняет пароль уже созданного PG volume. Не публикуйте порт в Internet. Для удалённых соединений настройте TLS и сеть отдельно.

## Операции

`npm run db:generate` генерирует клиент. `npm run db:deploy` применяет уже существующие миграции к `DATABASE_URL`; проверить адрес БД до запуска. Миграции тестировать на отдельной восстановленной БД. Не запускать `migrate dev` на production.

Выполненный аудит не менял БД и не читал строки пользователей. Нужны отдельная проверка `pg_hba.conf`, параметров TLS/listen, grants на объектах, размера/заполнения таблиц и ревью заявленных миграций владельцем DBA.
