# Резервное копирование

## Скрипт и политика

`scripts/backup.sh` создаёт custom `pg_dump` из Compose service `postgres`, архив исходников/Prisma/миграций/тестов/документов без `.env`, `node_modules`, data volume и generated client, затем шифрует весь контейнер AES-256 через GPG. Скрипт проверяет расшифровку, список объектов PostgreSQL, целостность tar и checksum до публикации. Он не удаляет существующие копии автоматически.

Подсказочные пороги проверки хранения: до 14 `daily`, 8 `weekly`, 12 `monthly`. Это не утверждённые сроки хранения и не автоматическая retention-политика. При превышении порога скрипт выдаёт предупреждение и сохраняет все старые копии. Планировщик **не включён** автоматически. Настраивать его можно только после утверждения срока хранения, отдельной копии вне основного хоста, контроля доступа, мониторинга и процедуры восстановления.

```sh
/absolute/path/to/MiryoLove\ Server/scripts/backup.sh daily
/absolute/path/to/MiryoLove\ Server/scripts/backup.sh weekly
/absolute/path/to/MiryoLove\ Server/scripts/backup.sh monthly
```

Назначьте daily один раз в день, weekly раз в неделю, monthly раз в месяц — не запускайте все три часто. Сначала проверить доступное место, отдельный filesystem, владельца/права, расписание и мониторинг результата. Данные не отправляются в облако. Backup по умолчанию хранится в `backups/` проекта, mode `0700`; содержимое только зашифровано, Git игнорирует каталог. Это отдельное от PG volume место, но **не off-host и не полноценная disaster recovery копия**.

## Первый запуск

Требуются Docker Compose, `gpg`, `pg_restore`, `tar`, `gzip`, `sha256sum`. Установить passphrase вне репозитория и сохранить отдельную резервную копию ключа в одобренном владельцем защищённом офлайн-месте:

```sh
install -d -m 700 "$HOME/.config/miryolove"
umask 077
openssl rand -hex 32 > "$HOME/.config/miryolove/backup-passphrase"
chmod 600 "$HOME/.config/miryolove/backup-passphrase"
scripts/backup.sh daily
```

Потеря passphrase делает архив невосстановимым. Не помещать ключ рядом с зашифрованными backup и не добавлять в Git/тикеты. При наличии действующего backup-passphrase сначала согласовать путь через `BACKUP_PASSPHRASE_FILE`. Скрипт требует mode `0600`.

Проверка контрольной суммы: из каталога архива выполнить `sha256sum -c <файл>.sha256`. Не удалять старые резервные копии вручную до проверки новой копии и восстановления.

## Ограничения и восстановление

Пока не настроен планировщик, нет гарантии, что копия регулярно создаётся. Одну начальную зашифрованную daily-копию проверили расшифровкой и восстановили в удаляемый контейнер PostgreSQL на изолированной Docker-сети; проверены шесть таблиц и две применённые Prisma-миграции. Запуск приложения/API на восстановленной копии и периодическое расписание этим не проверены. Для будущих восстановлений распаковывать только во временный защищённый каталог; использовать изолированную PostgreSQL instance без публичного порта и удалять только точно идентифицированный тестовый контейнер/volume. Никогда не указывать production `DATABASE_URL` как цель restore.

Backup включает пользовательские данные; доступ к файлам, passphrase, логи и retention должны быть ограничены и иметь подтверждённое владельцем основание/срок хранения. Скрипт проверяет, что passphrase не находится внутри каталога архивов, но само расположение ключа по умолчанию остаётся на том же хосте. Это не обеспечивает защиту от потери/компрометации всего сервера. Не удалять старые backup автоматически или вручную, пока владелец не утвердил retention и не проверена пригодность копии, предназначенной к сохранению.

## Результат проверки и ограничения

- Изменение: автоматическое удаление backup выключено; при превышении ориентировочного порога выводится предупреждение. Дополнительно скрипт отклоняет passphrase-файл внутри каталога backup.
- Проверка: `bash -n scripts/backup.sh`; автоматический тест проверяет отказ при passphrase внутри каталога backup до обращения к Docker; ранее созданная копия была расшифрована и восстановлена в отдельный временный PostgreSQL контейнер, не в production.
- Осталось: новая копия вне основного хоста, хранение ключа вне хоста, утверждённые сроки хранения, планировщик, периодический restore drill и проверка checksum должны быть организованы владельцем. Ничего из этого не настраивается автоматически.
